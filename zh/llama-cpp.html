使用 llama.cpp 运行本地模型 ​

Pi 支持 llama.cpp 的路由服务器（router）。路由器会发现多个 GGUF 模型并按需加载或卸载。

请使用支持 router 的较新 llama.cpp 构建。参考构建说明，或为你的平台安装预构建版本。

启动路由器 ​

启动 llama-server 时不带 --model 或 -m。传入模型会进入单模型模式而不是路由器模式。

bash
llama-server \
  --models-dir ~/models \
  --no-models-autoload \
  --jinja \
  --host 127.0.0.1 \
  --port 8080 \
  -ngl 999 \
  -c 32768

重要选项：

  • --models-dir ~/models 发现本地 GGUF 文件。
  • --no-models-autoload 保持通过 /llama 显式加载。
  • --jinja 启用兼容的聊天模板和工具调用。
  • -ngl 999 尽可能多地把层卸载到 GPU。
  • -c 32768 为每个已加载模型设置上下文窗口。省略则使用模型原生上下文，但可能需要显著更多内存。

单文件模型可以直接放在模型目录中。多模态模型和多分片（multi-shard）模型放在单独的子目录中：

text
~/models/
├── llama-3.2-1b-Q4_K_M.gguf
├── gemma-3-4b-it-Q4_K_M/
│   ├── gemma-3-4b-it-Q4_K_M.gguf
│   └── mmproj-F16.gguf
└── large-model-Q4_K_M/
    ├── large-model-Q4_K_M-00001-of-00003.gguf
    ├── large-model-Q4_K_M-00002-of-00003.gguf
    └── large-model-Q4_K_M-00003-of-00003.gguf

手动添加文件后重启路由器。要为每个模型设置上下文大小等选项，使用 llama.cpp model presets。针对特定 NVIDIA GPU 和模型的设置，参见 Run Pi with NVIDIA RTX and llama.cpp。

配置 Pi ​

启动 Pi 并配置提供商（provider）：

text
/login llama.cpp

输入路由器 URL 和可选的 API key。默认 URL 为 http://127.0.0.1:8080。

如果用 --no-models-autoload 启动路由器，/login llama.cpp 只保存连接信息。运行 /llama 加载模型，然后用 /model 为当前会话选择已加载的模型。

也可以通过环境变量配置这些值，无需 /login：

bash
export LLAMA_BASE_URL=http://127.0.0.1:8080
export LLAMA_API_KEY=optional-secret
pi

如果服务器使用 API key，启动 llama-server 时使用匹配的 --api-key。保留 --host 127.0.0.1 以仅限本地访问。

管理模型 ​

运行：

text
/llama
  • 选择未加载的模型来加载它。
  • 选择已加载的模型来卸载它。
  • 选择 Download model…，搜索 Hugging Face，然后选择仓库和量化（quantization）。也支持精确的 owner/repository[:quant] 值。
  • 在加载或下载过程中按 Escape 确认取消。

Hugging Face 搜索在设置了 HF_TOKEN 时使用它，随后依次检查 $HF_TOKEN_PATH、$HF_HOME/token、$XDG_CACHE_HOME/huggingface/token 和 ~/.cache/huggingface/token。无认证也可以搜索，但速率限制更低。下载受限（gated）仓库前 Pi 会警告并提供其访问页面链接。下载由 llama.cpp 服务器执行，因此当所选仓库需要访问权限时，其进程也必须有 HF_TOKEN。

如果已加载其他模型，Pi 会询问是先卸载它们还是保持加载。Pi 不会静默卸载模型，也从不删除模型文件。路由器可能与其他客户端共享，因此 /llama 总是显示路由器的当前状态。

已加载和休眠（sleeping）的模型会出现在 /model 中。休眠模型在被选中时自动唤醒。启用 router 自动加载时，未加载的预设（preset）模型也会出现并在被选中时加载。使用 --no-models-autoload 时，先通过 /llama 加载模型再选择。

如果路由器断开连接，/llama 显示 Retry 和 Close。Retry 重新连接并刷新模型状态，不重放被中断的操作。

分类模型 ​

分类器（classifier）模型回答关于 JSON 状态的输入式 choice、bool 和 score 问题，例如 TypeSafe 的 Jev 模型。模型从 codemode 脚本访问它们，扩展则通过 ctx.modelRegistry.classify()；参见分类器模型。Pi 以两种方式将 llama.cpp 模型列为分类器：

  • 决策模型（decision models），如 Julia-1、Laya、Kev、lev 和 OpenJev，通过 llama.cpp 的 /v1/systemone 端点原生回答。它们只作为分类器出现，使用 typesafe-system-one API，且不出现在 /model 中。
  • 聊天模型（chat models） 也会以相同 ID 和 llama-cpp-classify API 列为分类器，该 API 如下文所述从 next-token 概率读取答案。

llama.cpp 0.6.0 及更高版本会在路由器的模型列表中报告决策模型：其 architecture.output_modalities 包含 decisions。路由器从 GGUF 元数据中读取这一点，无需加载模型，因此 Pi 也能识别未加载和休眠的决策模型。较旧的 llama.cpp 构建不报告它，Pi 会将其决策模型列为聊天模型。

以聊天模型作为分类器 ​

模型不会生成答案。每个问题成为一条聊天提示词：状态、请求中的每个问题、再次出现的状态，然后是问题及其在单 token 标签（label）下的答案。标签对于 choice 是字母（最多 62 个选项），对于 bool 是 Yes/No，对于 score 是数字（最多 10 级）。状态以问题可见的方式被第二次读取，这在小模型的 JevBench 上提升了准确率。Pi 读取标签作为 next token 的概率并归一化。choice 返回每个选项的概率和置信度 (n * peak - 1) / (n - 1)；score 返回期望级别。

  • 原始标签概率通常过于自信。每次请求的 temperature 选项在归一化前缩放标签 logits；大于 1 的值使分布更平缓。它不改变答案。
  • 问题依次运行。一个请求的所有问题中，最后一个问题之前的内容都相同，因此服务器的提示词缓存只计算一次。状态出现两次，因此需要两倍于其大小的上下文。
  • 小模型可能遵循写在状态中的指令。提示词告诉模型将状态当作数据来判断，但这不构成保证。
  • Qwen3.5 等混合模型在没有上下文检查点（context checkpoints）时无法回退部分缓存的提示词。如果每个问题都重新处理整个状态，用 --ctx-checkpoints 32 --checkpoint-min-step 0 启动路由器。

故障排除 ​

检查路由器是否可达：

bash
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/models
  • /llama 中没有模型： 检查 --models-dir 和目录布局，然后重启路由器。
  • --no-models-autoload 时模型不在 /model 中： 先用 /llama 加载它。
  • 加载失败或内存占用过多： 降低 -c 或卸载其他模型。
  • 服务器不在路由器模式： 不带 --model、-m 或 -hf 启动。

要移除 llama.cpp 提供商和 /llama，在 pi config 的 Built-in 下禁用 llama.cpp，或在设置中设置 "extensions": ["-builtin:llama.cpp"]。
