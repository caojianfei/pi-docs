扩展 ​

扩展（extension）是为 Pi 添加可执行行为的 TypeScript 模块。当工作流需要工具、命令、事件处理器、模型 provider、会话状态或终端 UI，而不只是指令时，可以使用扩展。

扩展在 Pi 进程内部运行，拥有与该进程相同的操作系统权限。它可以检查提示词、工具调用、文件、凭据和会话历史，因此只应从可信来源加载扩展。

典型的扩展会添加 agent 工具、保护路径、确认危险命令、响应会话事件、修改上下文、暴露命令或显示持久状态。

创建并加载扩展 ​

扩展导出一个默认工厂函数，接收 ExtensionAPI。工厂为当前扩展运行时注册能力。

创建 ~/.pi/agent/extensions/hello.ts：

typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("hello", {
    description: "Show a greeting",
    handler: async (name, ctx) => {
      ctx.ui.notify(`Hello, ${name || "world"}!`, "info");
    },
  });
}

启动 Pi 并运行 /hello。开发期间可以直接加载文件：

bash
pi --extension ./hello.ts

Pi 使用 jiti，因此本地 TypeScript 扩展无需单独的编译步骤。分发的扩展和依赖请使用 Pi 包。

将扩展加入 Pi ​

把扩展放到你的用户或项目扩展目录中。Pi 会加载直接的 TypeScript 或 JavaScript 文件，以及包含 index.ts 或 index.js 入口的子目录。

小型扩展用单个文件，多文件实现用目录。把 npm 依赖放在附近的 package.json 中。约定位置见配置，其他路径见设置。

重新加载会替换扩展运行时，因此 await ctx.reload() 之后的代码不得复用旧运行时的状态。只有个人扩展和显式的命令行扩展可以参与在项目扩展加载之前触发的 project_trust 事件。

理解运行时生命周期 ​

工厂函数可以是同步或异步的。Pi 会等待异步工厂完成后再继续启动，因此它可以在启动期间获取配置或注册所需的 provider。

不要在工厂函数中启动进程、socket、watcher 或定时器，因为某些调用场景加载扩展时并不会启动会话。 长驻资源应从 session_start 或需要它们的命令或工具中启动。 会话级资源在幂等的 session_shutdown 处理器中关闭。

一次正常的提示会启动一个运行（run）。运行会重复多轮（turn），然后检查是否还有更多工作需要启动另一次底层 agent 运行：

mermaid
flowchart TD
    Input["input"] --> Before["before_agent_start"]
    Before --> AgentStart["agent_start"]
    AgentStart --> Turns[["turns"]]
    Turns --> AgentEnd["agent_end"]
    AgentEnd --> MoreRuns{"More work?"}
    MoreRuns -->|yes| AgentStart
    MoreRuns -->|no| BeforeSettle["agent_before_settle"]
    BeforeSettle --> Continue{"Continuation requested?"}
    Continue -->|yes| AgentStart
    Continue -->|no| Settled["agent_settled"]

更多工作指重试、恢复、压缩（compaction）重试或排队的工作。

每轮发送一次模型请求，并执行助手响应中的工具调用：

mermaid
flowchart TD
    TurnStart["turn_start"] --> Request[["model request"]]
    Request --> ToolDecision{"Tool calls?"}
    ToolDecision -->|yes| Tools[["tool execution"]]
    Tools --> TurnEnd["turn_end"]
    ToolDecision -->|no| TurnEnd
    TurnEnd --> MoreTurns{"Another turn?"}
    MoreTurns -->|yes| TurnStart
    MoreTurns -->|no| AgentEnd(["agent_end"])

模型请求按顺序执行这些钩子（hook）：

  1. context
  2. context_with_system
  3. before_provider_headers
  4. before_provider_request
  5. after_provider_response
  6. provider_stream_event 和助手消息事件

工具执行按顺序对每个工具调用执行这些钩子：

  1. tool_execution_start
  2. tool_call
  3. tool_execution_update（在工具执行期间）
  4. tool_result
  5. tool_execution_end

生命周期包括以下事件组：

领域事件
输入准备input、before_agent_start
Agent 运行agent_start、agent_end
模型轮次turn_start、context、context_with_system、turn_end
Provider 调用before_provider_headers、before_provider_request、after_provider_response、provider_stream_event
消息生命周期message_start、message_update、message_end
工具执行tool_execution_start、tool_call、tool_execution_update、tool_result、tool_execution_end
收尾agent_before_settle、agent_settled

运行启动期间（包括压缩检查和 before_agent_start）Pi 视为忙碌状态，因此期间发送的消息会进入正在启动的运行。消息生命周期事件也涵盖 user 和工具结果消息；模型请求列表只包含助手流在每轮中发生的位置。

工具钩子对每个工具调用执行，而一条助手响应可以通过返回工具调用来开启下一轮。Provider 钩子只在对应传输层暴露相应阶段时执行。确切的事件载荷和结果类型见 extensions/types.ts 中导出的声明。

会话启动和替换遵循单独的生命周期：

mermaid
flowchart TD
    Startup["Process startup"] --> Trust["project_trust when needed"]
    Trust --> SessionStart["session_start"]
    Switch["/new or /resume"] --> BeforeSwitch["session_before_switch"]
    Fork["/fork or /clone"] --> BeforeFork["session_before_fork"]
    BeforeSwitch --> Shutdown["session_shutdown"]
    BeforeFork --> Shutdown
    Reload["reload"] --> Shutdown
    Shutdown --> Replacing{"Replacing the runtime?"}
    Replacing -->|yes| Replacement["load replacement extension runtime"]
    Replacement --> SessionStart
    Replacing -->|no| Stop["process exits"]
    SessionStart --> Discover["resources_discover"]

project_trust 在受信任的项目资源加载之前运行，并且在会话替换进入新的工作目录时可以再次运行。重试、恢复、压缩和排队的消息可以在 agent_end 之后启动另一次 agent 运行，因此 agent_end 不是最终空闲信号。重新加载和会话替换会使旧运行时失效。await ctx.reload() 之后的代码仍属于旧运行时，不得复用其绑定会话的状态。

遵循扩展契约 ​

事件与并发 ​

处理器按扩展加载和注册顺序运行。pi.on() 返回一个用于取消该注册的函数；更改不影响正在进行中的分发。 有些事件是通知；另一些会转换数据、替换结果或取消操作。 使用每个事件声明的结果类型，不要假设每个返回值都有作用。

事件覆盖资源发现、会话、agent 和消息生命周期、provider、工具以及原始输入。

理解处理器组合方式 ​

模式行为
通知返回值被忽略。该事件仅用于观察。
原地修改后续处理器能看到 before_provider_headers.headers、before_agent_start.systemPromptOptions、tool_call.input 等值的变化。
链式转换后续处理器接收先前 input、context、context_with_system、message_end、tool_result 和 before_provider_request 处理器返回的值。
门控（gate）被处理的输入、被阻止的工具调用、被取消的会话操作或被处理的 user_bash 命令会阻止该操作走正常回退路径。
可行动边界每个 turn_end 或 agent_before_settle 处理器都能看到到目前为止提议的条目和延续决策。
最后覆盖返回动作的最后一个 cache_warming_decision 处理器生效。

通知处理器不应在流式事件上执行耗时操作。转换处理器应保留自己无意拥有的字段；门控处理器在无法做出安全决策时应默认拒绝（fail closed）。

before_agent_start 同时暴露当前提示词及其结构化的 systemPromptOptions。event.messageType 表明是什么启动了这次运行："user" 表示一次提示或 pi.sendUserMessage()，带有 prompt 和 images；"custom" 表示 pi.sendMessage(..., { triggerTurn: true })，带有起始 message 而没有 prompt。返回的 message 会加入这两种运行；通过检查 messageType 可以跳过由自定义消息启动的运行。优先修改提示词区块、选中的工具或准则（guidelines），这样 Pi 可以向对话记录追加增量。返回 systemPrompt 或设置 forceSystemPrompt 会替换该次运行的完整提示词，同时对话记录继续记录结构化的区块。Provider 会把强制文本作为其前导系统提示词。

message_end 可以在保留角色的情况下替换已定稿的消息。tool_call 可以修改输入或阻止执行。tool_result 处理器可以组合，每个处理器都能看到先前的更改。

provider_stream_event 在 Pi 归一化之前为每个解析后的 provider 流事件触发。该事件标识 provider、API 和模型；event.data 是 Pi 能获得的最早结构化值，不一定是原始 HTTP 字节或 SSE 帧。请将其视为只读，因为修改可能影响归一化。该事件是纯通知，不会持久化。

处理器按流顺序被 await，因此慢的处理器会延迟流的消费。处理器错误会被上报，但不会改变 provider 响应。可选的查看器见 debug-provider.ts，它按助手消息对原始事件进行分组。

context 在没有提示词和工具系统消息的情况下转换对话消息；Pi 事后会恢复这些状态。只有当请求局部（request-local）的转换必须拥有完整对话记录时才使用 context_with_system，并保持索引零处为系统消息。

turn_end 和 agent_before_settle 是可行动边界。它们的处理器可以链式追加提议的 custom、custom_message、context_edit 或 compaction 条目，并返回 continue: true 来请求下一次模型请求。要对延续条件做防护，因为无条件的延续会造成循环。完整的校验和排序契约见导出的事件声明。

cache_warming_decision 可以用 { action: "warm" } 或 { action: "stop" } 覆盖空闲时的提示词缓存刷新。返回动作的最后一个处理器生效。

一条助手消息中的多个工具调用可以并行运行。 不要在其他工具事件运行时假设同级调用或结果存在。 属于活跃轮次的嵌套工作使用 ctx.signal；命令和空闲会话事件通常没有操作信号。

返回 undefined 的 user_bash 处理器会把命令传给下一个处理器；如果没有处理器处理，则交给本地执行。返回 operations 或 result 会停止传播。处理器失败会阻止该命令，而不会回退到本地执行。

工具 ​

自定义工具定义名称、面向模型的描述、TypeBox 参数 schema 和 execute() 函数。 其结果需要面向模型的 content，以及用于渲染或状态重建的 details 字段。 没有结构化详情时使用 details: undefined。如果工具发起嵌套模型调用，应把它们的 usage 计入结果，以保证会话总量准确。

从 execute() 中抛出异常会产生失败的工具结果。 返回对象不会被标记为错误。 只有当该批次中每个已完成的工具都同意终止时，才返回 terminate: true 让 agent 跳过其自动后续步骤。

工具共享可变的内存状态时应使用顺序执行。 修改文件的工具应用 withFileMutationQueue() 包裹完整的读-改-写操作。 对面向模型的大型结果进行截断，并告诉模型去哪里读取完整输出。

当结果是数据时，声明 outputSchema 并返回匹配的 structuredContent。模型仍会收到 content；codemode 脚本等程序化调用方收到的则是 structuredContent 而非文本。没有 outputSchema 的工具会以文本内容传给脚本。要上报仍携带数据的失败，不要抛出异常，而是返回带 isError: true 的结果：模型看到错误，脚本仍能收到 structuredContent。

工具可以用 ctx.executeTool(name, args, { signal, onUpdate }) 运行其他工具。嵌套调用与模型发起的调用一样经过参数校验和 tool_call、tool_result 处理器，并发出 tool_execution_start、tool_execution_update 和 tool_execution_end；这些事件都带有 parentToolCallId，其 toolCallId 由 pi 分配为 <parent id>/<n>。这些 id 不会作为工具调用或工具结果出现在对话记录中。嵌套调用不添加对话记录条目：其结果只到达调用工具，由后者自行上报，例如通过 onUpdate 和 details。会话为它们保留一份有界的记录（名称、参数、状态、时长、错误；不含结果），存放在调用工具结果消息的 nestedCalls 中。它用于压缩文件列表，并显示在 HTML 导出中。每次调用超过 8 KiB 或每个工具结果超过 32 KiB 的参数会被省略，最多保留 256 次调用，complete: false 标记丢失内容的记录。嵌套结果的 usage（无论嵌套深度）会累加到调用工具的结果 usage 中，因此工具只上报自己的用量，不含其调用的工具。ctx.tools 列出 ctx.executeTool() 可调用的工具。对 content 做脱敏的 tool_result 处理器也应替换 structuredContent；只替换 content 会导致其被丢弃。

示例见 hello.ts、todo.ts、dynamic-tools.ts 和 truncated-tool.ts。

工具暴露 ​

exposure 控制模型如何触达某个工具。“可调用”（callable）指其他工具可以通过 ctx.executeTool()（ctx.tools）调用它，正如 codemode 工具的脚本所做的：

  • direct（默认）：激活时向模型声明，且激活时可被调用。
  • model-only：激活时向模型声明，永不可调用。用于编排其他工具或询问用户的工具。
  • codemode：注册后即可调用，并由 codemode 工具列出。除非显式激活，不向模型声明。
  • deferred：类似 codemode，但 codemode 工具不列出它；tool_search 可以找到并激活它。
  • hidden：已注册但不可触达。由于工具无法注销，可用 exposure: "hidden" 重新注册一个工具来撤回它。

namespace: { name, aliases, description, instructions } 将相关工具分组，如同 MCP 服务器那样。Codemode 工具在一个标题下列出命名空间及其 description。instructions 存放较长的使用指引；它不会被列出，codemode 脚本用 describeNamespace(name) 读取它。aliases 是脚本可以用来查找命名空间的其他名称，例如 mcp__docs 对应的服务器名 docs；名称以及作为脚本标识符的相同名字（my-docs、my_docs）的匹配方式相同。

注册 direct 或 model-only 工具会激活它；其他暴露方式在注册时不会激活。活跃工具集（pi.getActiveTools()、pi.setActiveTools()）是向模型声明的工具集合。pi.getAllTools() 报告每个工具的 exposure、namespace、annotations 和 reachesTools。

annotations 是关于工具用途的提示，含义与 MCP 工具注解一致：readOnlyHint、destructiveHint、idempotentHint 和 openWorldHint。MCP 工具携带其服务器声明的提示。缺失的提示采用 MCP 默认值：工具不是只读的，可能具有破坏性且可触达开放世界。这些提示不会被验证，但权限扩展可以用它们决定哪些调用需要确认。下面的代码确认了 Codex 请求批准的调用：

typescript
pi.on("tool_call", async (event, ctx) => {
  const hints = pi.getAllTools().find((tool) => tool.name === event.toolName)?.annotations;
  const needsApproval =
    hints?.destructiveHint === true ||
    (!hints?.readOnlyHint && ((hints?.destructiveHint ?? true) || (hints?.openWorldHint ?? true)));
  if (needsApproval && !(await ctx.ui.confirm("Allow tool call?", event.toolName))) {
    return { block: true, reason: `${event.toolName} was not approved` };
  }
});

编排其他工具的工具可以在其激活期间用 prepareLoadout(loadout) 调整模型看到的内容。它会在活跃工具每次变化时运行，并接收已声明的工具、可调用的工具以及每个已注册工具及其暴露方式、命名空间和提示词准则。它返回对已声明工具（包括它自己）的替换 descriptions，以及 hiddenDeclarations：保持活跃且可调用、但请求声明中省略的活跃工具。默认系统提示词的工具列表和规则中不包含隐藏工具，并且当文件读取器被隐藏时在技能提示中不点名任何工具，因此编排工具应自行展示它们的准则。codemode 只使用这个钩子、exposure、reachesTools 和 ctx.executeTool()，因此另一个工具可以用不同的名字实现相同行为。

触达其他工具的工具用 reachesTools(input) 声明一次调用可能触达哪些工具："all"，或输入中可能指代它们的词，其中一个词指名称包含它的每个工具或命名空间。codemode 对搜索或列出工具的脚本返回 "all"，否则返回脚本的词；tool_search 总是返回 "all"。较晚注册工具的扩展在其 tool_call 处理器中使用它，在调用运行之前完成注册该调用所需的工具，正如 MCP 扩展对仍在连接中的服务器所做的。MCP 扩展也只在同名工具声明了 reachesTools 时才为 MCP 工具激活 codemode 或 tool_search。

动态激活工具 ​

先注册所有工具，保持可选工具处于未激活状态，然后在加载器工具中使用 pi.setActiveTools() 选择期望的活跃工具。名称必须已经注册；未知名称会被忽略。

Pi 在对话记录的首条系统消息中记录初始提示词和工具集，然后在下一次模型请求之前追加工具和提示词的变化。无法表示这种转换的 provider 会收到完整的对话记录检查点，这可能使缓存的前缀失效。

工具渲染 ​

工具的 renderCall 和 renderResult 在交互式对话记录和 HTML 导出中绘制它的调用。pi.registerToolRenderer((toolName, next) => renderers) 为任意工具的调用选择渲染器，包括尚未注册的工具，例如会话恢复时其服务器尚未连接的 MCP 工具。next() 返回其余解析器（按扩展加载顺序）以及已注册工具会使用的结果，因此 next() ?? mine 只作补充。

MCP 服务器 ​

pi.registerMcpServer(name, config) 为当前会话添加一个 MCP 服务器。config 的形状与 mcp.json 中的 mcpServers 条目相同：stdio 服务器用 command、args、env 和 cwd，HTTP 服务器用 url、headers 和 oauth，另外还有 exposure、toolExposure、description、enabled 和 timeout。

typescript
pi.registerMcpServer("jira", { url: "https://mcp.example.com/jira", exposure: "codemode" });
pi.unregisterMcpServer("jira");

扩展加载期间注册的服务器在会话启动时连接，与 mcp.json 中的服务器一起；之后注册的服务器立即连接，pi.unregisterMcpServer() 会关闭连接并使其工具不可触达。注册不会被保存：每次加载时都要重新注册，例如基于扩展自身的设置。mcp.json 中同名的服务器优先，/mcp 会显示覆盖关系。再次注册同名会替换扩展先前的注册；由其他扩展注册的名称、无效名称和无效配置会抛出异常。

内置的 MCP 支持会连接已注册的服务器。当没有组件这样做时——例如被另一个扩展替换（见 MCP）——每次注册都会作为扩展错误上报。其他 MCP 扩展也可以连接已注册的服务器：在 session_start 中用 pi.getMcpServers() 读取它们，并处理 mcp_servers_change 事件以感知后续变化。

上下文与会话变更 ​

ExtensionContext 提供工作目录、模式、UI、会话管理器、模型运行时、中止信号、上下文用量，以及压缩和关闭的控制。 Provider 无关的嵌套模型调用使用 ctx.modelRegistry.streamSimple()。

命令处理器接收 ExtensionCommandContext，它增加了等待空闲、重新加载、树导航和会话替换的操作。 这些操作仅限命令使用，因为从生命周期处理器调用它们可能导致运行时死锁。

会话替换会使旧上下文失效。切换之前只捕获纯数据，然后使用 withSession 提供的新上下文进行会话绑定的工作。

UI 与模式 ​

ctx.ui 提供对话框、通知、状态文本、组件（widget）、标题、编辑器访问和自定义组件。 只有当交互需要自己的渲染和输入时才使用 ctx.ui.custom()。 组件、焦点、覆盖层、主题和性能指南见终端 UI。

扩展在交互、RPC、JSON 和 print 模式下都会加载。 交互模式提供完整的终端 UI。 RPC 可以通过 RPC Extension UI 协议转发支持的对话框和通知，但不支持自定义终端组件；JSON 和 print 模式没有 UI。 用 ctx.mode === "tui" 保护仅限终端的行为，并用 ctx.hasUI 判断交互式和 RPC 客户端支持的交互。

保持工具和事件行为独立于渲染，以便非交互模式仍然可用。

错误与清理 ​

Pi 会上报处理器错误并在可能时继续运行。tool_call 处理器失败会作为兜底阻止该工具；工具执行失败会成为给模型的错误结果。

即使正常操作已尝试清理，也要在 session_shutdown 中释放资源。 保持清理幂等，因为取消、重新加载、会话替换和进程退出可能汇聚到同一路径。 使用 ctx.shutdown() 请求有序的进程关闭。
