自定义提供商（Custom Providers） ​

提供商（provider）扩展把 Pi 连接到需要自定义认证、模型发现、请求处理或流式处理的模型服务。如果服务已经支持某个受支持的 API，请改在 models.json 中配置。

提供商扩展运行在 Pi 进程内部，可以查看凭据、提示词、工具定义、模型响应和用量。请把它们当作可信代码，避免记录机密或提供商载荷。

选择最小的集成方式 ​

需求使用
在受支持的 API 后添加模型models.json
修改现有提供商的端点或请求头models.json 或一个小型提供商扩展
动态发现模型带 refreshModels 的提供商
添加 /login 流程带原生或旧式 OAuth 配置的提供商
实现不受支持的传输协议带 stream 或 streamSimple 的提供商

提供商扩展是一种扩展，因此遵循相同的加载、信任、重载和错误行为。

注册提供商 ​

在扩展工厂函数中调用 pi.registerProvider()。Pi 会等待异步工厂完成后再继续启动，因此在工厂中注册的提供商可用于启动时的模型选择和 pi --list-models。

有两种注册形式：

  • 注册来自 @earendil-works/pi-ai 的完整 Provider，获得原生的认证、过滤、发现、刷新和流式行为。
  • 以旧式配置形式注册提供商名和 ProviderConfig，供现有扩展使用。

拥有静态端点和模型元数据之外行为的新集成，优先选择完整 Provider。Pi 会在已注册的原生提供商之上叠加 models.json 覆盖。

对现有提供商只注册 baseUrl 或 headers 会保留其内置模型。旧式形式中提供 models 会在聊天、图片和分类器操作中整体替换该提供商的模型。省略 type 表示 "chat"；图片和分类器模型需要显式的判别字段，并通过 images 和 classifiers 字段提供按其 api 值索引的实现。

重定向现有提供商 ​

只注册需要改变的字段。这样保留提供商内置的目录、认证、API 实现和兼容性设置：

typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerProvider("anthropic", {
    baseUrl: "https://gateway.example.com/anthropic",
    headers: {
      "X-Gateway-Key": "$GATEWAY_API_KEY",
    },
  });
}

保留上游协议的代理或网关使用这种形式。不要把内置模型列表复制进扩展——那会把一个小的端点覆盖变成会逐渐漂移的目录替换。

注册兼容端点 ​

当服务实现了受支持的协议但有自己的模型目录时，注册端点以及该服务实际暴露的模型：

typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerProvider("acme", {
    name: "Acme AI",
    baseUrl: "https://api.acme.example/v1",
    apiKey: "$ACME_API_KEY",
    api: "openai-completions",
    models: [
      {
        type: "chat",
        id: "acme-chat",
        name: "Acme Chat",
        reasoning: false,
        input: ["text"],
        cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
        contextWindow: 128000,
        maxTokens: 8192,
      },
    ],
  });
}

不需要可执行的扩展行为时，这种情况优先使用 models.json。当注册依赖运行时发现、自定义认证，或与其他扩展功能共享代码时，使用扩展。

注册混合操作模型 ​

混合操作提供商可以同时注册非聊天模型及其实现：

typescript
pi.registerProvider("media-tools", {
  apiKey: "$MEDIA_TOOLS_API_KEY",
  models: [
    {
      type: "image",
      id: "image-v1",
      name: "Image V1",
      api: "media-images",
      baseUrl: "https://media.example.com/v1",
      input: ["text"],
      output: ["image"],
      cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
    },
    {
      type: "classifier",
      id: "classifier-v1",
      name: "Classifier V1",
      api: "media-classifier",
      baseUrl: "https://media.example.com/v1",
      input: ["text"],
      cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
      contextWindow: 64000,
    },
  ],
  images: {
    "media-images": { generateImages: async (model, context, options) => result },
  },
  classifiers: {
    "media-classifier": { classify: async (model, context, options) => result },
  },
});

模型级 baseUrl 优先于提供商端点。如果不提供 models 列表，所有操作的内置模型保持注册状态。不同操作中相同的模型 ID 仍是不同模型，包括其模型级请求头。

初始扩展加载之后的注册调用立即生效。使用 pi.unregisterProvider() 移除动态提供商，并恢复它所替代的内置行为。

完整的注册示例参见经过验证的 GitLab Duo 提供商，它把流式处理委派给内置 API 实现。

提供认证 ​

静态提供商可以从字面量、环境变量插值或命令解析 API key。这些值使用与 models.json 相同的语法：

  • $NAME 和 ${NAME} 读取环境变量。
  • 以 !command 开头使用命令输出。
  • $$ 输出字面量 $。
  • $! 输出字面量开头的 !。

当集成需要存储凭据、自定义解析、提供商作用域的环境或多种登录方式时，使用原生提供商认证。

OAuth 提供商提供显示名称、登录流程、token 刷新和访问令牌解析。注册后会出现在 /login 中，Pi 把返回的凭据存入 ~/.pi/agent/auth.json。

OAuth 回调与 UI 无关。它们可以打开授权 URL、显示设备码、报告进度、请求输入，或让用户选择登录方式。网络请求期间要尊重取消操作和传入的 abort 信号。

按 Enter（tui.select.confirm）打开设备登录 URL 并复制代码，或手动登录。提供商可以在 onDeviceCode 或原生 AuthEvent 通知中用 openBrowserOnConfirm: false 或 copyCodeOnConfirm: false 禁用任一操作。

绝不要把访问令牌、刷新令牌、授权头或完整的提供商响应写入普通日志。

提供和刷新模型 ​

每个模型都需要 ID、显示名称、输入能力和成本元数据。聊天和分类器模型还需要上下文窗口；聊天模型需要输出上限和推理支持；图片模型声明输出模态。API 实现在提供商层级选择，除非某个模型需要单独覆盖。

当 Pi 应保持空闲提示词缓存温热时，把 promptCache.short 或 promptCache.long 设为该提供商尽力而为的缓存寿命（秒）。不设置则禁用对应保留层级的缓存预热。

兼容性标志描述的是已验证的差异，不要仅凭端点自称兼容就启用。

对照实际服务器确认请求字段和响应行为。

当可用目录来自在线服务时使用 refreshModels。把 context.signal 传给阻塞 I/O，使调用方可以取消刷新。

两种注册形式有不同的刷新契约：

  • 完整 Provider 不返回值。它调用 context.publish({ update }) 安装提供商自有的模型状态，之后其同步的 getModels() 暴露最新列表。
  • 旧式 ProviderConfig.refreshModels 返回混合操作的模型定义。Pi 用返回的列表替换该注册的实时模型，并应用请求的持久化。

只有需要跨运行保留的目录数据才发布为持久化数据。llama.cpp 这类在线服务可以只更新内存中的列表而不持久化；远程目录可以保留快照用于离线启动。

复用受支持的流式 API ​

只要提供商协议匹配，就使用 Pi AI 的某个 API 实现。

受支持的实现覆盖 Anthropic Messages、OpenAI Chat Completions 和 Responses、Google Generative AI 和 Vertex、Azure OpenAI Responses、Mistral Conversations 以及 Bedrock Converse。

提供商仍可以自定义认证、baseUrl、请求头、模型过滤和发现，同时把请求转换和流式处理委派给现有 API 实现。

这比复制一份流式实现更安全，因为它保留了 Pi 的消息转换、工具处理、用量统计、取消和兼容性行为。

实现自定义流式处理 ​

只有在没有任何现有 API 实现能表达该服务时才实现 streamSimple。先研究 packages/ai/src/api 下的实现。

流接收规范化后的 TranscriptContext。系统提示词和工具声明位于 transcript 的系统消息中，因此用 getCurrentSystemPrompt(context.messages) 和 getCurrentTools(context.messages) 读取它们，而不是期望 context.systemPrompt 或 context.tools。支持会话中途系统消息的模型可以原位接收；否则调用 collapseSystemMessages(context) 把后续系统消息折叠进开头那条。

自定义流必须：

  1. 创建一条助手消息，包含 provider、model、timestamp、待定 stop reason、内容和归零的 usage。
  2. 请求设置成功后，在内容事件之前发出一个 start 事件。
  3. 在发出配对的文本、思考和工具调用事件的同时更新消息。
  4. 最终确定 usage、cost、内容和 stop reason。
  5. 恰好发出一个终止 done 或 error 事件并关闭流。
  6. 把取消转换为 aborted 结果。

请求设置可能在 start 之前失败；此时流可以直接以 error 终止。缺少请求认证时也可能在返回流之前同步抛出异常。

内容索引指向助手消息中的块。先更新块，再发出通过 partial 字段暴露该状态的事件。工具调用参数在 toolcall_end 时必须包含有效的已解析输入。

流还必须遵守通过 SimpleStreamOptions 提供的请求插桩：

  • 在发送提供商请求前调用 options.onPayload，并使用它返回的替换载荷（如有）。
  • 在收到响应后、消费其 body 前调用 options.onResponse。
  • 对每个解析出的提供商事件，在规范化之前 await options.onProviderStreamEvent?.(providerEvent, model)。
  • 透传 abort 信号和提供商作用域环境。

这些钩子支撑扩展的请求检查、响应头事件和提供商流观察。省略它们会使该提供商的行为与 Pi 内置提供商不同。

报告失败与用量 ​

设置明确具体的终止 stop reason。错误和中止的消息需要 errorMessage；成功的消息需要准确的输入、输出、缓存、总 token 和成本值。

对可识别的上下文溢出错误，Pi 可以压缩并重试。如果服务使用未知的报错消息，在受保护的 message_end 处理器中只把该提供商的溢出响应规范化为 context_length_exceeded。

不要把限流或提供商的瞬时故障改写成上下文溢出。那些失败走 Pi 的正常重试行为。

测试集成 ​

至少测试：

  • 普通和空文本响应
  • 工具调用与工具结果
  • 支持时的图片输入和图片工具结果
  • 用量与成本统计
  • 中止行为
  • 上下文溢出
  • 畸形或部分流
  • Unicode 边界
  • 跨提供商的会话交接
  • 认证刷新与取消

packages/ai/test 下的提供商测试定义了内置提供商的预期行为。改编相关测试套件，不要只依赖手动提示词。

开发期间直接运行扩展，然后把它移动到被发现扩展的位置，或通过 Pi 包分发。在活跃会话中修改了被发现的提供商扩展后，使用 /reload。
